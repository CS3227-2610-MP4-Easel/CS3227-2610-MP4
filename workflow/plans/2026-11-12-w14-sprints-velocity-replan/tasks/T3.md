## Expected state
- T1 provides Replan schemas and endpoint contracts.
- `src/be/core/src/apply.ts` still reads/updates `aiProposal`; this is the behavior to remove.
- `src/be/contracts/src/frozen.ts` keeps the public Core and Sessions signatures unchanged.
- `src/be/llm-gateway/src/sessions.ts` owns current session authorization and outcomes.

## Objective
Create `@agile/proposals` with ProposalService, exact project → proposal → session → domain locking, immutable applied IDs in JSON payload, proposal creation/supersession, approval/rejection and transaction-aware session close. Refactor Core.applyReplan to domain-only while retaining frozen validation responsibilities.

## Rules that apply
- Proposal lifecycle is PENDING → APPROVED/REJECTED/SUPERSEDED; terminal states do not change.
- Approved replay returns stored applied IDs and ACCEPTED without inspecting a new subset; REJECTED/SUPERSEDED returns 409.
- Session binding requires proposal session ID, same project, LEAD_DIGEST, current environment, OPEN state; endpoint 48 requires owner.
- Core validates strict suggestion schema, actor role/membership, project scope/writability, referenced state and events, but never proposal tables.

## Contract
[contract] `ProposalService.list/createReplan/createReplanInTransaction/approve/reject` and exact `closeInTransaction(tx, {sessionId, proposalId, projectId, feature, ownerId, outcome, actorId})`. A selected Suggestion is `{id,type:MOVE_CHECKPOINT_DATE,checkpointId,newTargetDate,rationale}`, `{id,type:MOVE_EPIC_TO_CHECKPOINT,epicId,checkpointId|null,rationale}`, or `{id,type:REASSIGN_TASK,taskId,assigneeId,rationale}`. Approval passes selected full objects in request order to Core and stores `appliedSuggestionIds` in payload. All failures roll back proposal/domain/session rows.
