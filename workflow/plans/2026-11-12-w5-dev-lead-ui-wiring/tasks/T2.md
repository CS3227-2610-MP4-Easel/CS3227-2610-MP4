**Delivers:** Typed live clients and DTOs for endpoints 6,7,9,10,12,13,16,17,20,21,22,23,24,33.
**Satisfies:** F1,F2,F3,F4,F5,F6,E4,E9,E11,E12,E13,E15. **Depends on:** - **Wave:** 1 **Weight:** complex

## Expected state
- `src/fe/lib/api/index.ts` contains prototype helpers and W8 clients.
- `src/fe/lib/api/types.ts` lacks the complete W5 live DTO/page types.
- Backend page queries default to zero-based `page=0,size=20`.

## Objective
Add distinct live functions and types without changing prototype signatures. Serialize supported filters,
encode IDs, include versions on mutations, and never serialize `sprintId` for W5 task updates.

## Rules that apply
- F1-F6 Clients match the frozen endpoint paths and use `apiFetch`.
- N1 Nested IDs are validated by the backend; the client never invents authorization.

## Contract
All calls use `apiFetch` and return JSON DTOs. Use these exact client contracts:

| Client | Request | Result |
|---|---|---|
| `listProjects_6(page=0,size=20)` | `GET /api/projects?page&size` | `Page<ProjectDetail>` |
| `getProject_7(projectId)` | `GET /api/projects/{projectId}` | `ProjectDetail` |
| `getProgress_33(projectId)` | `GET /api/projects/{projectId}/progress` | `Progress` with totals, percent, unestimated count and velocity |
| `listMembers_9(projectId)` / `addMember_10(projectId,email)` | `GET/POST /api/projects/{projectId}/members`; POST `{ email:string }` | `Member[]` / `Member` |
| `listCheckpoints_12/createCheckpoint_13(projectId)` | `GET/POST /api/projects/{projectId}/checkpoints`; POST `{ name:string,targetDate:string }` | `Checkpoint[]` / `Checkpoint` |
| `listEpics_16/createEpic_17(projectId,page,size)` | `GET/POST /api/projects/{projectId}/epics`; POST `{ title:string,description?:string|null,checkpointId?:string|null }` | `Page<Epic>` / `Epic` |
| `listTasks_20(projectId,page,size,filters)` | `GET /api/projects/{projectId}/tasks?page&size&status?&epicId?&assigneeId?&blocked?` | `Page<Task>` |
| `createTask_21(projectId,input)` | `POST /api/projects/{projectId}/tasks`; `{ epicId:string,title:string,description?:string|null,acceptanceCriteria?:string[],storyPoints?:number|null,assigneeId?:string|null }` | `Task` |
| `getTask_22(taskId)` / `updateTask_23(taskId,input)` | `GET/PATCH /api/tasks/{taskId}`; PATCH allows title, description, acceptanceCriteria, storyPoints, assigneeId and required `version` | `Task` |
| `setTaskStatus_24(taskId,input)` | `POST /api/tasks/{taskId}/status`; `{ status:string,blocked?:boolean,blockedReason?:string|null,version:number }` | `Task` |

`ProjectDetail` contains project fields plus `progress`; `Member` contains `userId,displayName,role,addedAt`.
Checkpoint, Epic and Task resources carry IDs, project relationship, timestamps and `version`.
Task status values are passed through exactly as returned by the backend enum; story points are `null` or one of `1,2,3,5,8,13`.
Create timeout/network errors are not auto-retried. Member add reloads and deduplicates by `userId`.
Cross-project task and nested IDs retain normal 404/validation behavior without mutation.
