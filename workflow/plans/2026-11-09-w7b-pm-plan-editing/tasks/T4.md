## Objective
Regenerate can claim a DONE epic, keep its previous tasks until the store, bump the proposal `version` when the new tasks land, and a locked pre-check returns what the flow needs before the session cap is spent. A second regenerate that started from an older proposal version cannot claim. Endpoint 37 behaviour is unchanged.

## Rules that apply
- Default `mode` is `"EXPAND"` and behaves exactly as today. Only `"REGENERATE"` treats a DONE row as claimable (sets IN_PROGRESS, lease, allocated epic version, error null; tasks untouched).
- Every actual claim in either mode, under the proposal lock, allocates `1 + max(payload.epicVersionWatermark or 0, all current epic versions)`, writes it to both the claimed row and `payload.epicVersionWatermark` in the same transaction, merging existing payload fields. Above 2,147,483,646 throw CONFLICT_STATE without changes, reserving one increment for store or fail. Test successful allocation at the boundary and rejection beyond it. A rejected claim or DONE response allocates nothing.
- In REGENERATE mode, after `lockProposal`, a given `expectedProposalVersion` that differs from `proposal.version` throws `ProposalError("CONFLICT_VERSION")` before the epic is touched.
- `failEpic` returns `Promise<boolean>`: `true` when it wrote FAILED, `false` when its guard failed (nothing written). Existing callers ignore the value. On a failed regenerate the epic becomes FAILED and its previous tasks remain.
- `guard` returns `{ proposal, row }` so `storeEpic` can write `version: proposal.version + 1` in the same single `aiProposal.update` that sets `flagged` when both apply (never two updates). `payload.edited` is not touched.
- A live IN_PROGRESS epic cannot be claimed in either mode (existing CONFLICT_STATE).
- `precheckRegenerate` checks the index range after `guardEdit` (a stale version beats an unknown index; this differs from endpoint 37 on purpose).

## Contract
```ts
// expand-store.ts [contract]
claimEpic(db, { proposalId, index, actorId, now?, mode?: "EXPAND" | "REGENERATE", expectedProposalVersion?: number }): Promise<ClaimResult>   // REGENERATE never returns kind "DONE"
storeEpic(db, { proposalId, index, claimedVersion, tasks, flagged, bumpProposalVersion?: boolean }): Promise<PlanEpic>
failEpic(db, { proposalId, index, claimedVersion, error }): Promise<boolean>
export async function precheckRegenerate(db: FilteredDbClient, i: { proposalId: string; index: number; actorId: string; version: number; now?: Date }): Promise<{ sessionId: string; status: "PENDING" | "DONE" | "FAILED" }>;
```
`precheckRegenerate` runs in one transaction: `guardEdit` check order (404 for another creator or an archived project, CONFLICT_STATE unless PENDING, CONFLICT_VERSION), then index not an integer in range: NOT_FOUND; the epic live: CONFLICT_STATE; returns the proposal's `sessionId` and the epic's effective status (an expired-lease IN_PROGRESS row reports `PENDING`). It writes nothing except the lock.
