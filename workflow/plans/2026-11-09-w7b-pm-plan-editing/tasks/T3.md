## Objective
Two store functions in one transaction each, with the same check order, creator rule, proposal-lock-first ordering, whole-plan validation and `edited` marking as T2. Both return the fresh `PlanProposal` view.

## Rules that apply
- Check order: `guardEdit` (lock, 404, CONFLICT_STATE unless PENDING, CONFLICT_VERSION), then body rules.
- Primary key of `proposal_epics` is `(proposal_id, index)`: re-key with one `update` per row, never one multi-row decrement.
- Proposal `version` +1 and `payload.edited = true` on every success, merging into the payload.
- Epic rows: every delete allocates `1 + max(payload.epicVersionWatermark or 0, all current epic versions)` under the proposal lock, stores it as the watermark and each shifted row's version; above 2,147,483,646 throw CONFLICT_STATE without changes (reserve one increment for store or fail); `contentHash`, status, tasks and error of a shifted row stay.

## Contract
```ts
// epic-list.ts [contract]
export async function addEpic(db: FilteredDbClient, i: { proposalId: string; actorId: string; version: number; title: string; description: string; checkpointName: string | null }): Promise<PlanProposal>;
export async function deleteEpic(db: FilteredDbClient, i: { proposalId: string; actorId: string; version: number; index: number; now?: Date }): Promise<PlanProposal>;
```
`addEpic`: appends at `index = current count`, `expansionStatus` PENDING, `tasks` null, `contentHash = epicContentHash(...)`. More than 10 epics after the add: VALIDATION_FAILED("epics") (the whole-plan check). `checkpointName` not null and not a name in `payload.checkpoints`: VALIDATION_FAILED("checkpointName").
After the transaction commits, both return `getProposalView(db, proposalId, actorId)`; a `null` view throws `ProposalError("NOT_FOUND")`.
`deleteEpic`: the index is checked after `guardEdit` (a stale version beats an unknown index; this differs from endpoint 37 on purpose): not an integer in `0..count-1`: NOT_FOUND. Only one epic: VALIDATION_FAILED("epics"). Any epic of the proposal live (`isLive`): CONFLICT_STATE (nothing changes). Otherwise lock the deleted epic and every later epic in ascending order, delete the row, then for each later row in ascending order `update` its `index` to `index - 1` and `version` to the allocated watermark value.
