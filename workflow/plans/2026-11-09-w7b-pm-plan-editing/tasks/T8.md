## Objective
The six endpoints are served with strict bodies, per-endpoint byte limits that run before authorisation, index parsing that answers 404 for malformed indexes, and resolvers that map each to its proposal or project. Edits, regeneration and approve work end to end against the real database in mock mode.

## Rules that apply
- Body limits (raw bytes, `before` hook, as the existing routes): 38: 262,144; 58: 16,384; 59: 32,768; 39: 1,024; 36 and 60 have no body.
- Index (38, 39, 60) must match `^(0|[1-9][0-9]{0,2})$` else 404 NOT_FOUND without calling the flow.
- Handlers never check roles or ownership; the policy gate (role PM, MEMBER) and the store do.
- Success: 59 answers 201; 36, 38, 39, 58, 60 answer 200; edits return `PlanProposal`.
- Resolver choice is deliberate: `PM_PLAN_CREATE` is in the W5 project operations, so an archived project reaches the existing GET rule and answers 404 for endpoint 36.
- Resolver: `PROPOSAL_OPERATIONS` gains `PM_EPIC_UPDATE`, `PM_EPIC_REGENERATE`, `PM_PROPOSAL_CHECKPOINTS_UPDATE`, `PM_PROPOSAL_EPIC_CREATE`, `PM_PROPOSAL_EPIC_DELETE`; `PM_PROPOSAL_LIST` resolves exactly as `PM_PLAN_CREATE` does (call `resolveCoreResource(resolvers, "PM_PLAN_CREATE", request)`); do not edit `core/src/resolvers.ts`.
