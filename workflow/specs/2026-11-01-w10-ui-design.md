## 1. Problem
Architecture §13 names eleven screens with one line each. It does not say what a page contains, which role sees which control, what each page shows when empty, loading, failed or read-only, or how a role moves from one page to the next. Every other workstream (W4 to W9) links its flows to the UI that W10 draws (AD-71), so without a concrete reference they would build against guesses, and the demonstration path could not be walked end to end.

Desired: one reference that states, for every screen of every role, its contents, interactions and states; mockups of all of those screens that a reviewer can click through; and, once the operator has confirmed the mockups, a standalone prototype that mirrors them. Tier 1 mockups are due 2 Nov 2026 and Tier 2 by 5 Nov 2026 (AD-71). W10 draws; it does not wire any screen to the backend.

## 2. Goals
**Functional**
- F1 The reference covers 20 screens (the inventory in `ui.md` §1). Each has its layout regions, interactions with endpoint numbers, role visibility and states, and every endpoint 2 to 57 maps to at least one screen. Acceptance: a reviewer finds no endpoint in `contracts.md` that is missing from the coverage table, and no screen without its interactions listed, as a table or a list.
- F2 Mockups exist for all 20 screens, with the shell, the shared components and one sheet of global states. Each screen shows its populated state and the states its screen file lists, and offers each role only the controls that role may use (`ui.md` §6). Acceptance: the Tier 1 screens by 2 Nov and the Tier 2 screens by 5 Nov can be clicked through for the demonstration path in `flows.md` (the seven flows of `flows.md`).
- F3 Each mockup element that depends on a contract change not yet made is marked as such, and each change is sent to its owner as a handover (endpoint 6 shape, endpoint 36 tier, endpoint 42 path and policy, future standup date for endpoints 51 and 52). Acceptance: the branch state lists one open handover per change, and the fallback used if the owner refuses is recorded in edge cases E36 to E39.
- F4 After the operator confirms the mockups, a standalone prototype reproduces them from static fixture data, with no backend calls. Acceptance: every screen of F2 opens in the prototype, and each difference from the mockups is listed in the branch state.

**Non-functional**
- N1 Status is never carried by colour alone: every status chip has a text label and an icon. All user, AI and uploaded text is drawn as plain text (A-15). The board is fully operable without a pointer through the **Change status** menu.
- N2 Colour, type, spacing, radius and elevation values are defined once as design tokens and mirrored as CSS variables; one `AppShell` serves all roles, with role-based navigation items and no per-role copy of the layout (R6).

## 3. Non-goals
- Wiring any screen to an endpoint, Firebase or a database - W4 wires sign-in and register (W4 spec SD4), the module owners wire the rest.
- Building `apps/web` or its folder layout - W1 owns the scaffold.
- Mobile layouts, a dark theme and translations - the design target is a 1280 px desktop and the light theme (`ui.md` §2).
- Changing the policy map, an endpoint or a tier - W10 asks for the four changes in F3 by handover; the owners decide.
- Real data, seeded accounts and the demo database - W13.
- New features beyond the 57 endpoints - a screen needs an endpoint in `contracts.md`, otherwise it is not drawn.
