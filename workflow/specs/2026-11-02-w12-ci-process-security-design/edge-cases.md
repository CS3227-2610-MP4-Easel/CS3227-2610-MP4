# W12 Edge Cases

| ID | Requirement | Scenario | Expected behaviour (exact) | Why it matters | Test layer |
|---|---|---|---|---|---|
| E1 | F1, N3 | A PR changes application code | All seven required checks run and each result is visible by its stable name; a missing check blocks merge | Prevents an apparently green PR with a skipped control | integration |
| E2 | F2 | The lockfile is stale or an install script is present | `npm ci --ignore-scripts` exits non-zero for lock drift and executes no dependency lifecycle script | Stops CI from testing a different graph or running untrusted install code | integration |
| E3 | F3, F4 | A policy entry has no generated OpenAPI operation | The contract check exits non-zero and identifies the missing operation | Prevents route-policy drift | integration |
| E4 | F5, F12 | A staged file contains a test canary that matches the scanner rule | Local scan exits non-zero; CI scan also exits non-zero | Proves both enforcement points measure the same risk | unit/integration |
| E5 | F5 | A documented false positive is added | Only the exact reviewed rule/file pattern is ignored; another matching file still fails | Prevents broad secret-scan bypasses | integration |
| E6 | F6, N1 | The audit service is unavailable or its advisory database changes | The dependency-audit check fails closed on unavailable service and records the advisory source/input; N1 does not claim identical results across advisory updates | Avoids treating an unevaluated dependency set as safe | integration |
| E7 | F7 | A workflow references an Action by tag, branch, unapproved repository, or non-40-character SHA | `workflow-security` exits non-zero and identifies the file and reference | Prevents mutable or unapproved supply-chain inputs | integration |
| E8 | F8, F10, F13 | An agent or PR edits its own permission policy, adapter, CODEOWNERS, workflow, or scanner config | The policy check fails closed and GitHub requires the two trusted people other than the PR author; self-approval cannot satisfy either role | Prevents self-authorized control changes | integration/manual |
| E9 | F8, F13 | Attack-corpus text contains instruction-like content | The adapter passes it as data, denies protected-path writes, and requires the two trusted people other than the PR author, one per role | Tests the A-17 process threat | manual |
| E10 | F9 | A required check is skipped, a stale approval remains after a new commit, the author approves, or a branch has no CODEOWNER approval | GitHub reports the branch blocked and refuses merge on both `development` and `main` | Ensures repository settings enforce the written policy | manual |
| E11 | F9 | A user attempts direct push, force push, deletion, or administrator bypass on either protected branch | GitHub rejects the operation | Prevents bypass of review and checks | manual |
| E12 | F11, N2 | A PR comes from a fork or an untrusted same-repository branch | The `pull_request` workflow has no secrets/environments, uses a hosted runner and `permissions: {}`, does not use `pull_request_target`, and cannot deploy or write | Prevents secret exfiltration through untrusted code | manual |
| E13 | F5, F12 | A secret is in a renamed file, an earlier PR commit, or the scanner allowlist is widened | CI scans the checked-out tree and PR commit range; protected configuration changes require review and broad/stale allowlists fail the policy check | Prevents scan-scope and configuration bypasses | integration/manual |
| E14 | N3 | A command prints a secret-like environment value or a check fails | The workflow does not provide credentials to the job, records the command and exit status, and retains failure output without the canary value | Logs are durable and externally visible | manual |
| E15 | N1, N4 | W1 has not yet merged into INT | W12 spec and policy work may proceed, but implementation checks that consume W1 scripts remain gated until the W1 base is available | Keeps dependency order explicit | manual |
| E16 | F13 | A sensitive PR is authored by any one of the trusted people | The security-review check requires the other two trusted people exactly once, with one security-reviewer approval and one human approval; either role assignment passes | Prevents author self-approval while retaining a two-person independent review | unit/integration |
| E17 | F13, N2 | One or both required GitHub reviews are missing, stale, dismissed, or not `APPROVED` for the exact PR head | The security-review check fails; only the two current GitHub approvals satisfy sensitive-path review | Prevents self-asserted or stale approval evidence | integration |
| E18 | F13 | A sensitive PR supplies the author as either reviewer, supplies the same person for both roles, or omits one of the other two trusted people | The security-review check fails closed; the author cannot review, the roles must be distinct, and both non-author trusted people are required | Prevents self-authored or single-person approval | unit/integration |
| E19 | F13 | A required reviewer approves, then submits `CHANGES_REQUESTED` or has the approval dismissed at the same head | The latest review state is `CHANGES_REQUESTED` or `DISMISSED`, so the security-review check fails until a new approval is submitted | Prevents withdrawn or superseded approval from remaining valid | integration |
| E20 | F13 | The GitHub reviews endpoint returns multiple pages | The checker fetches and evaluates every page before deciding whether both current approvals exist | Prevents a missing later review from causing a false failure or false pass | integration |
| E21 | F14 | The initial W12 PR has no base-branch sensitive-path manifest but adds the exact bootstrap manifest | T6 uses the fixed bootstrap list, validates an exact head-manifest match, and continues with dual exact-head GitHub reviews | Allows the initial rollout without trusting an arbitrary PR policy | integration |
| E22 | F14 | The initial PR omits, changes, reorders, or malforms the bootstrap manifest | T6 fails closed before classifying paths or accepting review evidence | Prevents the bootstrap path from becoming a PR-controlled policy | unit/integration |
| E23 | F14 | A later PR's base branch contains a malformed or missing manifest | T6 fails closed and does not re-enter bootstrap mode | Prevents repeated fallback after the initial rollout | integration |
| E24 | F14 | The first PR targets `main`, uses a different base SHA or PR number, or changes the head manifest's whitespace, key order, path order, keys, or duplicate paths/keys | Only whitespace/key-order variation passes parsing; wrong target/base/PR number, path order, unknown keys, duplicate keys, duplicate paths, or a changed list fails closed | Binds bootstrap to one rollout and makes equality deterministic | unit/integration |
| E25 | F14 | A later PR deletes or malforms the head manifest while the base manifest is valid | T6 fails closed on the head manifest before accepting review evidence | Prevents policy poisoning or denial through an invalid control file | integration |
| E26 | F14 | Two PRs use the pre-rollout base SHA, or the bootstrap variable remains after the first merge | Only the externally configured PR number can enter bootstrap; after variable removal, all later attempts fail closed | Prevents parallel or repeated bootstrap | integration/manual |
| E27 | F14 | The first rollout evaluator, fixed list, and head manifest are reviewed only informally | Gate 3 requires the two trusted reviewers other than the PR author to compare all three against the approved contract and record the base SHA, target, PR number, merged head, and variable removal | Compensates for the evaluator being introduced in the bootstrap PR | manual |
| E28 | F15 | A required review is submitted after a failed gate | After the trusted workflow has been independently landed on the default branch, the workflow runs and publishes a fresh `workflow-security` result for the current exact PR head; a valid pair can change the required check to pass | Prevents an approval from leaving a valid PR blocked | integration/manual |
| E29 | F15 | A required approval is edited, dismissed, or replaced by `CHANGES_REQUESTED` | After the trusted workflow has been independently landed on the default branch, the workflow runs and publishes a fresh `workflow-security` result that fails unless both latest records are exact-head `APPROVED` reviews | Prevents stale approval status from remaining green | integration/manual |
| E30 | F16 | The CLI receives an impossible base SHA or wrong bootstrap PR number | The command exits non-zero and does not silently load the PR-local manifest | Prevents a PR from bypassing trusted-base validation through argument-name drift | integration |
| E31 | F17 | A sensitive file is renamed to a non-sensitive path | With rename detection disabled, Git emits `D` for the source and `A` for the destination; both are classified, so sensitive review is required | Prevents protected-file relocation bypass | unit/integration |
| E32 | F18 | `npm test` runs under Windows `cmd.exe` | Test discovery completes without `$()` expansion and includes all repository test files | Keeps the standard command usable across supported contributor shells | integration |
| E33 | F15 | A review event arrives after a new commit changes the PR head | The trusted workflow compares the event head with the current GitHub PR head and fails closed; the next `synchronize` event evaluates the new head | Prevents an old review event from publishing a result for the wrong commit | integration/manual |
| E34 | F15 | GitHub review API or fork-head object fetch fails | The trusted workflow exits non-zero and does not publish a passing required result | Prevents incomplete review data or missing Git objects from becoming approval | integration/manual |
| E35 | F15 | A non-sensitive PR receives review events | The trusted workflow publishes a passing `workflow-security` result without requiring sensitive approvals | Preserves ordinary non-sensitive PR flow | integration/manual |

## What could corrupt data

W12 does not write application data directly. A compromised workflow could still corrupt the
repository or deployment state by merging unreviewed code, changing Prisma migrations, altering the
policy map, weakening the scanner, or deploying with production credentials. Required checks,
protected branches, `CODEOWNERS`, default-deny agent policy, read-only PR tokens, protected scanner
configuration, and the production-secret boundary prevent those paths. A failed check or unavailable
audit fails closed; no recovery migration or production rollback is performed by W12.
