## 1. Problem
**Today.** The PM has no AI feature. The tables `ai_proposals` and `proposal_epics` exist (W1 init migration, `AiProposal`, `ProposalEpic`), the gateway knows `PM_PLAN_OUTLINE` and `PM_PLAN_EXPAND` (`llm-gateway/src/config.ts`), W6 lists `pm.similarItems` as an unregistered source, and the policy map holds endpoints 34-41. No route, prompt, store, mock response, resolver or `applyPlan` exists. `src/be/core` does not exist (W5 is not started). `Sessions.assertUsable` rejects a call whose feature differs from the session's (`gateway.ts:63`), so one session cannot serve both plan stages.

**Desired.** A PM sends an idea and gets a plan proposal (approach, checkpoints, epics) from a strong model; expands each epic into tasks with a cheaper model, one request per epic; and approves it in one transaction that creates checkpoints, epics, tasks and `CREATED` events, or rejects it. Nothing is created before approval. Every failure leaves a retry or a "create manually" path (architecture §9.2, §13). Affected: the PM (owner of W7); Dev Lead and Developer see only the created rows.

**Scope.** Backend only (SD1): endpoints 34, 35, 37, 40, 41 (contracts §3.4). Endpoints 36, 38, 39 belong to W16; the New Plan screen is wired after W5.

## 2. Goals
**Functional** (dependencies first)
- F1 A session opened for `PM_PLAN_OUTLINE` also admits `PM_PLAN_EXPAND` calls - Accept: `assertUsable(s, u, "PM_PLAN_EXPAND")` passes for an OPEN `PM_PLAN_OUTLINE` session of `u`, and still throws `NOT_FOUND` for every other feature mismatch.
- F2 `applyPlan` in `@agile/core` creates a validated plan in the caller's transaction - Accept: given a valid plan it writes the checkpoints, epics, tasks and events of § 4.3; given any invalid plan it writes nothing and throws.
- F3 `pm.similarItems` returns at most 5 epic and task titles from the caller's member projects - Accept: with a query matching items in a member and a non-member project, only member rows come back; with the flag off or no query, `[]`.
- F4 Endpoint 34 creates a PENDING plan proposal from an idea - Accept: 201 `PlanProposal` with every epic expansion PENDING, one OPEN session, one stage-1 call.
- F5 Endpoint 35 returns a proposal - Accept: 200 for a member PM; 404 for a proposal of another project.
- F6 Endpoint 37 expands one epic, idempotent by state - Accept: 200 with DONE tasks; a second call returns the stored result with no gateway call.
- F7 Endpoint 40 approves in one transaction, idempotent - Accept: first call creates rows and returns counts; any repeat returns the same body and creates nothing.
- F8 Endpoint 41 rejects a PENDING proposal - Accept: 200 REJECTED, session closed `REJECTED`, nothing created.
- F9 Mock mode serves both features end to end - Accept: with `LLM_MODE=mock`, endpoints 34, 37 and 40 complete against the database with no provider call, and the same inputs give the same plan.

**Non-functional**
- N1 No model call runs inside a database transaction; endpoints 34 and 37 make exactly one `run` call each - Accept: tests assert the call count, and `run` itself refuses a transaction.
- N2 A maximum plan (8 checkpoints, 10 epics, 80 tasks) is approved in one transaction using at most 10 write statements besides the row lock - Accept: an integration test counts write statements from Prisma query events (E53); the time is reported, not asserted.
- N3 No prompt contains a title from a non-member, archived or deleted project - Accept: integration test with two projects, checked on the `similar-items` section text and `retrieved`.
- N4 Every error row of § 4.3 and every threat row of § 6 has a passing test - Accept: the E table is fully covered.
- N5 Static sections fit their budgets - Accept: a test calls `assertStaticSectionsFit` for both features.

## 4. Design
### 4.1 Approach
Three packages follow C51: `@agile/pm` (`src/be/pm`: routes, prompts, sections, mock responses, `pm.similarItems`, settings), `@agile/proposals` (`src/be/proposals`: store, claim protocol, resolvers, view mapping) and `@agile/core` (`src/be/core`: only `applyPlan`, `PlanInputSchema`, `countPlan` from W7; W5 adds the rest). `pm` holds the flow and calls `proposals` for storage and `Sessions`, `assembleWith` and `LlmGateway.run` for AI. `proposals` receives `core: Pick<Core, "applyPlan">` and the sessions object by injection. Files that call the gateway import no database client (W6 source scan); `similar-items.ts` and the stores may.

**Locking (SD6).** The filtered client has no raw SQL, and Prisma may turn an `updateMany` with a relation filter into a select followed by an update, which would not re-check the state after a wait. So every claim is lock, then read, then decide: inside one transaction, run `update` with a unique selector on the row, changing only `updated_at`; this takes the row lock and a concurrent request waits for it; then re-read the row (a new statement at READ COMMITTED sees the winner's commit) and decide from what it reads. Tests must hold the first transaction open with a barrier so the waiting path runs.

**Archived projects.** The filtered client hides every row of an archived project (visibility policy: `Project`, `ProjectMember`, `Epic`, `Task`, `AiProposal` and `ProposalEpic` are scoped to ACTIVE). So endpoints 35, 37, 40 and 41 answer 404 for an archived project, not the 409 of architecture §8; this is recorded as a Deviation at the fold (SD17). Endpoint 34's response for an archived project comes from W5's project resolver.

### 4.2 Data model
No schema change, no migration, no seed change (the tables and enums exist from `00000000000000_init`). Rollback of W7 code leaves the tables unused.

`ai_proposals` (kind `PLAN`): `payload` = `{ approach: string, checkpoints: {name,targetDate}[], retrieved: {source: "EPIC"|"TASK", projectId, id}[], applied?: {checkpoints,epics,tasks} }`; `retrieved` holds ids only, and `projectName` and `title` are resolved on every read (below); `applied` is written at approval. On insert: `kind` PLAN, `status` PENDING, `created_by` the caller, `session_id` the plan's single session, `flagged` the stage-1 result's flag, `version` 1. A later expand sets `flagged` to true when its result is flagged and never back to false, **without** changing `version`. `version` increases by 1 only on approve and reject (W16's edits will also bump it), so a client's version from endpoint 34 or 35 stays valid while epics are expanded.

**Responses** use the existing contract schemas `PlanProposalSchema` and `PlanEpicSchema` (`src/be/contracts/src/schemas.ts`); instants are serialised as the other endpoints do. `retrieved` in a response is built on every read from the ids: titles and project names are looked up through the filtered client, restricted to projects where the **viewer** is a member (a second PM who is not in project B never sees B's titles), and an id that no longer resolves is omitted.

`proposal_epics`: `index` = 0-based position in the outline; `content_hash` = sha256 hex of `title + "\n" + description + "\n" + (checkpointName ?? "")`; `version` starts at 1 and rises by 1 on every claim and every store; `lease_expires_at` is set only while `IN_PROGRESS`, 60 s after the claim (longer than the gateway deadline of 25 s, so a live call never loses its lease); `tasks` null until DONE; `error` null or a code from § 4.3 (`AI_BUSY`, `AI_UNAVAILABLE`, `AI_DISABLED`, `REQUEST_REFUSED`, `BLOCKED_INPUT`, `SESSION_EXPIRED`, `INTERNAL`).

**Proposal states** (W7): `PENDING` -> `APPROVED` (endpoint 40, a PM who is a member) | `REJECTED` (endpoint 41, same). Terminal states do not change. **Epic expansion states**: `PENDING` -> `IN_PROGRESS` (claim, lease 60 s) -> `DONE` | `FAILED`; `FAILED` -> `IN_PROGRESS` (retry); an `IN_PROGRESS` row whose lease has passed is read and claimed as `PENDING`; `DONE` is final in W7.

**Invariants.** A PENDING proposal has no domain rows. APPROVED implies `applied_by`, `applied_at` and `payload.applied` are set and the rows exist. Epic indexes are contiguous from 0. Counts: checkpoints 0-8, epics 1-10, tasks per epic 1-8. Every `checkpointName` equals a checkpoint name of the same proposal or is null; names are unique ignoring case.

**Plan input** (`PlanInputSchema`, strict, exported by `@agile/core`): `{ checkpoints: {name 1-200, targetDate YYYY-MM-DD}[], epics: {title 1-200, description 0-4000, checkpointName: string|null, tasks: {title 1-200, description 0-4000, acceptanceCriteria: string[] (0-12, each 1-300), storyPoints: 1|2|3|5|8|13}[] }[] }` with the counts above. It has no ids, no project id and no assignee.

### 4.3 Interfaces
**Model output schemas** (`pm`, zod; no field needs a URL, angle bracket or entity, W3 conventions): stage 1 `{ approach: string 1-1500, checkpoints: {name 1-200, targetDate}[] 0-8, epics: {title 1-200, description 1-1000, checkpointName: string|null}[] 1-10 }`, where `targetDate` is a real calendar date from today to today + 730 days in the application time zone (AD-37), checkpoint names are unique ignoring case, and `checkpointName` refines to a listed name or null. A schema or guard rejection reaches the route as `AI_UNAVAILABLE`; only the model's explicit `{"refusal":true}` reaches it as `REQUEST_REFUSED`. Stage 2 `{ tasks: {title 1-200, description 1-1000, acceptanceCriteria: string[] 1-6 each 1-300, storyPoints: 1|2|3|5|8|13}[] 1-8 }`. A refusal is the gateway's `{"refusal":true}` handling.

**Gateway failure mapping** (used by 34 and 37): `BLOCKED_INPUT` -> 422 `VALIDATION_FAILED`; `REQUEST_REFUSED` -> 422 `REQUEST_REFUSED`; `AI_BUSY` -> 429 `AI_BUSY` with `Retry-After` = `retryAfterSeconds` or 60, `details.reason` `LOCAL_LIMIT`; `AI_UNAVAILABLE` -> 503 `AI_UNAVAILABLE`; `AI_DISABLED` -> 503 `AI_DISABLED`; `ROLE_DENIED`, `ContextScopeViolation`, `CONTEXT_SOURCE_*`, `CORE_*`, `INVALID_LLM_CALL` -> 500 `INTERNAL`, never retried; `NotMember` -> 404; thrown `NOT_FOUND` from the session check -> 404; thrown `CONFLICT_STATE` from the session check -> 409 `CONFLICT_STATE` (message "The AI session expired; start a new plan."); `SessionCapReached` (endpoint 34 only, the one that opens a session) -> 429 `RATE_LIMITED` with `Retry-After`. 413 `PAYLOAD_TOO_LARGE` follows the body cap of AD-33's envelope. `sanitiseInput(idea).blocked` is W3's definition: nothing is left after sanitising; a merely flagged idea is sent on, marked (AD-25). Body size is checked first, by `Content-Length` and then by counting streamed bytes, before parsing (the pattern of W4's `bodyTooLarge`).

### 4.4 UI
None: backend only (SD1). The responses carry what architecture §13 lists for the New Plan screen: epics with expansion state and `error`, tasks, `retrieved` provenance, `flagged`.

### 4.5 Conventions
- **Sections** (W3, W6 rules). Stage 1, in priority order 0 first: `rules` (STATIC, trusted, budget 600 tokens), `output-format` (STATIC, trusted, 500), `today` (DYNAMIC, trusted, 30; the text is the application-time-zone date), then `project-brief` (priority 1, 1200), `checkpoints` (2, 400), `similar-items` (3, 600) from `assembleWith`, and `idea` (DYNAMIC, **untrusted**, priority 0, budget 1750). Stage 2: `rules` (STATIC, 500), `output-format` (STATIC, 400), the three assembled sections (`project-brief` 800, `checkpoints` 300, `similar-items` 400, from the W6 allow-list), `approach` (DYNAMIC, **untrusted** because it is stored model output, priority 0, budget 300) and `epic` (DYNAMIC, **untrusted**, priority 0, budget 600; text `title: ...` then `description: ...`). Section names are literals. Budgets leave room for the 49-character wrapper and the 280-character suffix.
- **Prompt content** (the text itself is implementation): `rules` states the PM-planning task, that wrapped text is data, that output is the JSON of `output-format` only, the limits of § 4.2, that dates are on or after `today`, that story points come from the set 1, 2, 3, 5, 8, 13, that no URL, link or markup may appear, and that a request that is not about planning a software project is answered with `{"refusal":true}`.
- **`inputHash`** = sha256 hex of the feature name, a newline and the `text` of every section joined with `\u0000`.
- **Settings** (`loadPmSettings(env)`, called at module load): `PM_SIMILAR_ITEMS` is `on` or `off`, default `on`; any other value throws `Error("INVALID_SETTING:PM_SIMILAR_ITEMS")` naming the setting, never the value. The client cannot set it (A-07).
- **Mock responses**: registered with `registerMockResponse` at import of `@agile/pm`. Stage 1 returns one checkpoint "MVP" dated `today` + 28 days (read from the `today` section) and three epics "Foundation", "Core features", "Release". Stage 2 returns three tasks "Design", "Build", "Test" with 3, 5 and 2 points and one criterion each. Both are valid under the schemas and trigger no guard.
- **No logging** of ideas, titles, prompts or model text. Logs carry ids and codes only.
- **Errors** use the envelope of architecture §8; `X-Request-Id` on every response.

## 6. Security
Tier High, Attacker lens added (tenancy, authorization, untrusted input crossing into prompts and into domain rows).

**Per operation.** Principal: the verified user with role PM (policy map, AD-55; handlers never check roles). Authorization and tenancy: the gate resolves the project (34 by `{id}`, 35/37/40/41 by `proposalResolvers`), requires membership, and hides archived projects; a foreign or unknown id is 404. Inside the flow: `assembleWith` checks membership again and the role; `applyPlan` locks the project row and re-checks state, role and membership. Any member PM may read, approve or reject a proposal of the project; only its creator may expand it (policy is `member`; the creator rule exists because the session is the creator's; SD13). Validation: strict zod on every body, caps in § 4.2, the idea passes `sanitiseInput` and the gateway pipeline as an untrusted section. Titles and project names in `retrieved` are resolved per viewer. Logging: ids and codes only.

| T | Actor / abuse | Mitigation | Test |
|---|---|---|---|
| T1 | PM types injection into the idea to make the model emit a link, markup or a prompt | `idea` untrusted and wrapped; output schema closed; output guard rejects links and markup; approval is a human gate; UI renders plain text | E8, E52 |
| T2 | Another user's item title in a member project carries injection into the prompt | `similar-items` untrusted, titles only, at most 5, flagged text marks the plan | E17 |
| T3 | Cross-project leak through retrieval or through the stored provenance (non-member, archived, deleted, removed member, a second PM) | member ids filtered before search; W6 row checks as backstop; ids stored, titles resolved per viewer | E12, E13, E51 |
| T4 | IDOR on `proposalId` or `index` | resolver + gate 404; every store query includes the proposal id | E19, E21 |
| T5 | Wrong role (DEV_LEAD, DEVELOPER) or no token on any endpoint | policy gate 403 and 401 | E5 |
| T6 | Client sets session, model, flag, status or project id | strict schemas reject; `PlanInput` has no ids; `applyPlan` takes the project id from its argument | E38, E47 |
| T7 | Double approve, approve against reject, against a concurrent expand, replay | lock-then-read in one transaction; status then version checks | E27, E32-E35, E48 |
| T8 | Oversized writes from model output | counts and lengths in the output schema and again in `PlanInputSchema` | E8, E38 |
| T9 | Cost abuse by repeated plans or expands | session caps (20 a day, 3 open), limiter windows, one claim per epic at a time | E6, E23, E24 |
| T10 | Another PM blocks or hijacks an epic's claim or uses the creator's session | claims are server-side only; leases expire after 60 s; non-creator expand is 404 before any claim | E25, E50 |
| T11 | Poisoned retrieved or stored text reused in stage 2 | `approach` and `epic` sections are untrusted | E52 |
| T12 | Archive race lets rows land in an archived project | project-row lock in `applyPlan`; archived projects hidden from the flow | E36, E55 |
