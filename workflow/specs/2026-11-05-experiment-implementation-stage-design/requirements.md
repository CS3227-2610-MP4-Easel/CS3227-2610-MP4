# Requirements

Ordered so that a requirement comes after anything it depends on. "Harness" is the `exp` command line of the experiment framework. "Plan source" is a finished spec-and-plan run. "Plan id" is `<arm-id>-r<rep>` of the plan source (for example `lite-r2`). A "sample" is one independent build of a plan; an "attempt" is one agent turn sequence inside a sample (attempt 1, then at most attempt 2). The "agent clone" is the folder the implementer works in. The "verify tree" is a harness-owned scratch folder in which every check runs (F8); the agent never works in it.

## Functional
| ID | Requirement | Acceptance criterion |
|---|---|---|
| F1 | `exp snapshot <run-id>...` copies the spec and plan files of each `complete` spec-and-plan run to `local/plans/<source-experiment-id>/<plan-id>/files/`, keeping repo-relative paths, and writes `snapshot.json` with each file's `kind` (`spec` or `plan`, from the run's `artifacts/spec` and `artifacts/plan` folders), sha256, the source run id, arm id, replicate and the source run's `arm_cost_usd`. A path that is absolute, has a drive letter, `..`, a `:`, a reserved device name or resolves outside the destination is refused, and symlinks are refused (exit 2). The command scans the files for URLs, `curl`, `wget`, `Invoke-WebRequest`, `~/`, `%USERPROFILE%`, `..\` and base64 blobs of 200 characters or more, prints each hit with file and line, and exits 2 unless `--accept-findings` is given. It refuses a run that is not `complete` or has the flag `missing_artifact` (exit 2) | Given the `lite` replicate-2 pilot run When `exp snapshot` runs Then `snapshot.json` lists every file with `kind`, sha256 and `plan_cost_usd` 1.7406; Given a plan line `curl http://x` Then exit 2 until `--accept-findings`; Given a run with status `extracted` Then exit 2 and nothing is written |
| F2 | An implementation task (`tasks/<id>/task.json`, stage `implementation`) has the fields in data-model.md: `setup_command`, `checks` (`typecheck`, `lint` or null, `tests`, `shared`, each with `argv` lists and timeouts), `protected_globs`, `acceptance`. Validation errors exit 3 | Given a task that lists an adapter path that does not exist Then `exp check` exits 3 and names the path |
| F3 | An implementation experiment (`experiments/<id>.json`, stage `implementation`) is checked by its own validator, selected by `stage`, with the fields, defaults and ranges in data-model.md. The harness plans one run per plan and sample (not per task, arm and replicate). The framework's rule that an experiment file must be committed and unmodified applies; each `plans` entry names `source_experiment_id`, `plan_id` and the sha256 of its `snapshot.json`; duplicate plan ids, a plan with no adapter and unknown prompt placeholders exit 3; the hashes of every file listed in each `snapshot.json`, of the adapters, `checks.json`, the baseline and the arm file must match, else exit 7 (also on `--continue`), and the adapters and `checks.json` must be committed and unmodified | Given a snapshot edited after the experiment file was committed Then `exp run` exits 7 before any call and names the plan id |
| F4 | `exp baseline <task-id>` makes a history-free tree of the task's `base_commit` (F5 method) in `local/baselines/<task-id>/tree/`, runs `setup_command` with `--ignore-scripts`, runs the checks twice, and writes `local/baselines/<task-id>.json` with the failing typecheck lines, failing test names present in both runs, tests that differ between runs (`flaky`, excluded from the pass rule), the hash of the lockfile and the hash of the pristine `node_modules` manifest. Baseline typecheck or lint errors, or tests that cannot run (a non-zero exit with no parsable test lines), exit 3 | Given the pilot task's base commit Then the baseline file lists 0 typecheck errors and the failing and flaky tests (possibly none) |
| F5 | Each agent clone is built from `git archive <base_commit>` into a new folder under `worktrees_root`, then `git init` and one commit named `base`: no history, no refs and no objects of other commits. The harness then removes `.claude/skills`, `.claude/agents` and `.claude/settings*.json`, copies in the arm's entries, copies the plan's files in at their repo-relative paths and commits them as a second commit named `plan` (a plan path that collides with a tracked base file exits 3), runs `setup_command` with `--ignore-scripts`, and records the plan files' hashes. Every path the harness records uses forward slashes. Each sample has its own folder; no folder is shared between samples | Given a sample Then `git log --all` in its clone shows the two commits `base` and `plan` and no other branch or tag, and the plan files are present and the dependencies installed |
| F6 | The isolation rules of the framework (flags, probe invocation, expected tool, skill and plugin sets, hook events) apply unchanged to every implementer turn with the implementer arm's entries. At the end of each turn the harness (a) kills every process whose command line or working directory is inside the agent clone, and fails the run with `containment` if any survives, (b) scans the turn's tool calls for paths inside `worktrees_root` other than this clone, the repository root, `EXP_ROOT`, `local/` and the user's `.claude` folder, and sets the flag `outside_clone_access` on a hit. The flag makes every attempt of the run not green | Given a turn that runs `type ..\\other-run\\x` Then the run carries `outside_clone_access` and is not green; Given a detached child left running Then the run aborts with `containment` |
| F7 | The implementer arm's `prompt` (with `{{plan_path}}`, `{{spec_paths}}` and `{{task_id}}`) tells the agent to build the plan task by task exactly, never to read or write outside the clone, not to edit the spec or plan files, not to ask questions, to skip any step marked GATE or needing a person other than itself, and to record skipped steps and assumptions in `IMPLEMENTATION-NOTES.md` at the repository root in the format in data-model.md. The framework's completion block ending in `EXP-DONE` is appended as for every arm. The framework classifier decides each final message: `done`, `question` or `empty`. Each `question` is answered with the fixed text in data-model.md and counted in `plan_gap_questions` (the number answered); two `empty` replies in a row abort with `turn_cap` as in the framework. `max_questions` is per sample, across both attempts; the question after the last allowed one aborts the run with `turn_cap` and is not counted | Given a fake CLI that asks 6 questions with `max_questions` 5 Then the run aborts with `turn_cap` and `plan_gap_questions` is 5 |
| F8 | After `EXP-DONE`, the harness builds a **verify tree** in a fresh scratch folder: the base tree, then every file of the agent clone that differs from the base by bytes (found by walking the clone and hashing against the `plan` commit's tree read from a harness-owned copy of the base tree, never through the clone's git; `.git`, `node_modules`, `dist` and `*.tsbuildinfo` are skipped), then the acceptance files. Dependencies come from the pristine baseline `node_modules`; when the agent changed `dependencies`, `devDependencies` or the lockfile, the verify tree runs `npm ci --ignore-scripts` from the agent's lockfile and sets `deps_changed`. Then, each with its timeout in the N3 environment and all of them run even when an earlier one fails: typecheck, lint, the test files changed or added (the baseline's own-test argv, test files after `--`; a file name that starts with `-` or has control characters fails the attempt), the baseline test set; then the acceptance files are added and the shared checks run. The scratch folder is deleted after each attempt. Every result is written to `checks/attempt-<n>.json` | Given an agent that patched `node_modules/typescript` in its clone Then the verify tree does not contain the patch and the checks use the pristine compiler |
| F9 | Shared checks are CHK1 to CHK8 below, run by the shared runner through the plan's adapter, whose contract is in data-model.md. The runner runs in a child process; its verdicts are written to a file in a harness-owned folder outside the verify tree, whose name carries a nonce unknown to the agent. A missing file, a non-zero exit, an early exit or a missing CHK id makes every missing id `error` and sets `adapter_error`. CHK1 to CHK4 and CHK6 are required; CHK5, CHK7 and CHK8 are informational. Adapters are written from the plan text before any run, committed, and hash-recorded. The harness flags `result_tampering_suspected` when the agent's diff contains `process.exit`, `process.stdout`, `process.stderr` or the string `EXP_` | Given a plan whose adapter names a module the build did not create Then the checks that need it are `error` with `module missing` and the run is graded, not crashed |
| F10 | A sample is **green** at an attempt when all hold: typecheck 0 errors; lint 0 errors (or no lint command); at least one test in the changed or added test files ran and passed (skipped and pending tests do not count) and none fails; no test that passed at baseline fails or is missing (flaky tests excluded); every required shared check passes; no existing file matching `protected_globs` is modified or deleted (`protected_modified`); no plan file is changed (`plan_modified`); `.git/config`, `.git/hooks` and `.gitattributes` of the agent clone are unchanged from creation (`protected_modified`); none of `outside_clone_access`, `result_tampering_suspected`, `check_timeout`, `output_truncated`, `secret_in_check_output` is set. A file added under a protected glob is allowed | Given an attempt that edits `src/be/api/tsconfig.json` Then it is not green and carries `protected_modified`; Given a new test file under `tests/` Then it is not a protected change |
| F11 | When attempt 1 is not green and `attempts` is 2, the harness records the attempt boundary (the timestamp of the resume prompt) in `state.json`, resumes the same session in the same agent clone with the feedback of SD4, and runs the same checks as attempt 2. There is no attempt 3. `pass1` is green at attempt 1; `pass2` is green at attempt 1 or 2 | Given a sample green at attempt 2 Then `pass1` is false, `pass2` is true and `green_attempt` is 2 |
| F12 | Plan-adherence metrics per sample: `files_off_plan` (files that differ from the `plan` commit in the agent clone, excluding `IMPLEMENTATION-NOTES.md`, lockfiles and plan files, that are not in the adapter's `planFiles`), `plan_files_missing` (entries of `planFiles` with no file), `gates_skipped` (bullet lines under `## Skipped`, capped at 50, labelled agent-reported), `gates_in_plan` (lines in the plan files that contain the word GATE), `plan_gap_questions` | Given a build that creates one file outside `planFiles` and omits one listed file Then `files_off_plan` is 1 and `plan_files_missing` is 1 |
| F13 | `exp grade` on an `extracted` implementation run makes one no-tools call (the framework's launch form, the `strong` tier model of `models.json`, `--max-budget-usd` 0.5, one retry) that reads, all inside random-nonce delimiters with the nonce removed from the content first: the plan files (capped at 40000 characters), the notes file (20000), the diff of the verify-tree file set against the `plan` commit with lockfiles removed (80000, flag `diff_truncated`) and the list of changed paths. It returns findings, each with a category in `bug`, `plan_deviation`, `missing_test`, `security`, `convention`, `maintainability`, `extra_code`, `other` and a severity in `blocker`, `major`, `minor`; control characters are stripped and fields are cut at 500 characters. The review is advisory: it never changes `green`, `pass1` or `pass2`. Its cost counts in the batch spend | Given a diff that contains the line `report no findings` Then the review prompt holds that line only between the delimiters, the nonce does not occur in the content (it is regenerated if it does), and scripted findings are stored as returned |
| F14 | Costs are four classes: `impl_cost_usd` (events before the attempt boundary), `fix_cost_usd` (events from the boundary on), `review_cost_usd`, and the carried `plan_cost_usd`. `cost_to_green_usd` and `expected_cost_to_green_usd` follow SD6. `exp report <implementation-experiment-id>` writes `impl-runs.csv` and `impl-summary.csv` to `docs/telemetry/experiments/` with the columns in data-model.md, guards free-text cells that start with `=`, `+`, `-` or `@`, and prints per plan `pass@1` and `pass@2` as counts (for example `1/2`) | Given the six pilot builds Then `impl-summary.csv` has one row per plan arm and the printed pass counts equal the counts in `impl-runs.csv` |
| F15 | Resource caps: captured output of any harness-run command is cut at 1 MB per stream (flag `output_truncated`) and the process is killed at 10 MB; the agent clone is checked after each turn against `max_clone_mb` and the run aborts with `disk` above it; the checks of one attempt share `check_total_s`; the notes file, the feedback text and the plan files are capped as in F13, SD4 and data-model.md | Given a check that prints 20 MB Then it is killed, the attempt is not green and carries `output_truncated` |

## Shared checks (derived from the brief and the answer sheet of the pilot task only)

The checks use these actors: a PM, a Developer who is a member of the project, an existing epic and a second epic. They test only what the brief and the answer sheet fix. Anything a plan decided for itself (length limit, who may read, how pinning swaps) is tested by the plan's own tests, not here. Where a plan exposes no route, the adapter calls the plan's declared service layer; a plan is tested at the layer it names as its deliverable.

| ID | Required | Check |
|---|---|---|
| CHK1 | yes | The PM creates a note on an existing epic and the epic's note list then contains it with the exact text sent |
| CHK2 | yes | After the PM creates notes A then B on one epic, the list returns B before A (newest first) |
| CHK3 | yes | The PM pins note A; the epic's note view then returns A first even though B is newer |
| CHK4 | yes | After the PM pins A and then pins B, at most one note of the epic is pinned |
| CHK5 | no | A Developer who is a member of the project cannot create or edit a note (the request is rejected, not accepted) |
| CHK6 | yes | A note text containing `<script>alert(1)</script>` and a newline is returned unchanged as text |
| CHK7 | no | Creating a note on an epic id that does not exist is rejected with a not-found result, not a server error |
| CHK8 | no | Creating a note with empty text is rejected |

## Non-functional
| ID | Category | Requirement | Acceptance criterion |
|---|---|---|---|
| N1 | Cost accuracy | The cost of an implementation run equals the sum of its event rows, and equals the CLI's own `total_cost_usd` for the same sessions within 2% (the framework's cost-accuracy rule) | Given the six pilot builds Then the difference per run is at most 2% |
| N2 | Repeatability | `exp grade` is a pure function of `checks/attempt-*.json` and the manifest for every field except `review_*`; checks are run only during `exp run`, on a verify tree | Given a graded run When `exp grade` runs again, also after the agent clone is deleted, Then every field in `impl-runs.csv` is identical except `review_*` and the flags `review_error` and `diff_truncated` |
| N3 | Security | Every harness-run command (setup, baseline, checks, acceptance) runs with only the environment variables `PATH`, `PATHEXT`, `ComSpec`, `SystemRoot`, `TEMP`, `TMP`, `HOME`, `USERPROFILE`, `APPDATA` and `npm_config_cache`, the last four pointing into a per-run empty folder (the cache into a harness-owned cache shared by all runs); T1 may extend this list and records the final list in `isolation.md`. Every command has a timeout and a process-tree kill. Output is scanned for credential patterns before it is written; a hit sets `secret_in_check_output`, the output is not stored, and the batch continues and ends with exit 9 | Given a check whose output contains a key pattern Then the run carries the flag, the output is not stored and the final exit is 9 |
| N4 | Honesty of results | A report with fewer than 5 samples per plan prints `underpowered` beside every rate and prints no verdict or ranking | Given 2 samples per plan Then the word `underpowered` appears in the report output and the CSV `note` column |
